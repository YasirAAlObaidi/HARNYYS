yyai architecture

Draft agreed on 22 November 2026. No code exists yet. This page is the overview, and each decision has its own record in docs/decisions.

yyai is one Python program, built in strict layers, that we install on each client's own hardware. It answers customers on WhatsApp and staff in a web app. It reads the client's business software through swappable handlers, and it talks to an AI model that runs as a separate program wherever suits the client. Everything that differs between clients lives in configuration, not in code.

What yyai is

We install yyai for one client company at a time, on hardware in their office. Staff use it on the company network, and from outside over a VPN or Tailscale. Customers reach it through WhatsApp, which is the main channel for most clients. We are launching in the UAE, and expansion to other countries could come at any time.

Clients run different software. One client keeps stock and accounts in Al Ameen, which runs on Microsoft SQL Server, and uses Zoho as its CRM. Another uses something else. yyai has to fit each of them without becoming a different program for each.

The AI model can live anywhere: on the same machine, on another machine on the network, on a self-hosted cloud, or with a provider like Claude. Our first client has a custom-built PC with a 16 GB graphics card. The NVIDIA DGX Spark and the Mac Studio are other possible setups.

Principles

  • One program, strict layers. Everything runs in one process, and each layer may only call the layer directly below it.
  • Clients differ in config, never in code. Every client runs the same image, and a config file picks the products and the rules.
  • The model is just a service we call. It never touches data, sends messages or writes SQL. Our code does all of that.
  • Nothing is lost and nothing is sent twice. Every message and every agent turn is saved before work starts, and outgoing messages wait in a queue until they are delivered.
  • Vendor systems are treated carefully. Reads use a read-only login. Writes go only through tested tools, and only where a project allows them.
  • Arabic is built in from the start. It isn't added later.

Layers

There are six layers. A layer may only call the layer directly below it, and skipping a layer is forbidden. CI checks this on every change with import-linter.

LayerHoldsNever does
FrontendThe web app staff use.Talk to anything except the API.
EntryAPI routes, webhook endpoints and worker jobs. These are the ways work starts.Contain business rules.
WorkflowsUse cases that combine services: handling an inbound message, running an agent turn, delivering the outbox. The agent loop, its tool registry and its tools live here.Talk to handlers directly.
ServicesBusiness logic, one area each: pricing, catalogue, conversation, messaging, model, stock.Call each other or call upward. Combining services is a workflow's job.
HandlersAll communication with the outside: our database, the model server, and one brand handler per vendor product, plus shared connection helpers.Contain business rules or know about other handlers' products.

There are two exceptions. The core package (config, logging, errors and shared data types) may be imported by every layer, and imports nothing from them. bootstrap.py is the one place allowed to import every layer: at startup it reads the client's config, builds the brand handlers, plugs them into their jobs and builds the tool registry. The cost of strict layering is some pass-through code, where a simple read still goes through a workflow and a service. We accept that.

See decisions 0001, 0002 and 0003.

Jobs, brands, helpers

Business software is reached through three kinds of code. A job says what can be asked and what comes back. A brand handler answers those questions for one product and does the actual communication. A helper is shared connection code that brands use. Business logic only ever talks to jobs, so it never names a vendor.

Each client's config plugs exactly one brand into each job it uses:

# deployments repo: customers/acme/config.yaml
integrations:
  inventory:  al_ameen
  accounting: al_ameen
  messaging:  whatsapp_cloud
  crm:        zoho
  • A separate job exists only where a client could realistically use a different product for it. Merging inventory and accounting into one "database job" was considered and rejected.
  • One brand can fill several jobs. Al Ameen is one handler class that implements both jobs over a single SQL connection.
  • Helpers sit at the bottom of the handlers layer. Only handlers import them, and they know nothing about products.
  • We design the inventory job from Al Ameen plus one other real product. The accounting and POS jobs wait until a client needs them.

See the animation connection type vs job and decision 0005.

The model

The model always runs as a separate program, outside our Docker image, and we reach it over HTTP. Almost every model server speaks the same OpenAI-compatible format, including TensorFold, vLLM, Ollama, llama.cpp and LM Studio, so one handler covers them all. A second handler covers Anthropic's API for Claude. Each client picks a model server to suit their hardware.

Business code never names a model. It asks for a role, and config maps the role to a server:

models:
  chat.default:
    provider: openai_compat
    base_url: http://gpu-pc.lan:8080/v1
    model: local-model          # whichever model the client's GPU runs
    allow_external: false        # client data may not leave the building
    capabilities: {tools: true, context: 32768, arabic: good}
  chat.reasoning:
    provider: anthropic
    model: claude-opus-5-5
    allow_external: true         # only if the client agrees in writing

The model service, in the services layer, enforces these rules for every request:

  • A request never goes to an external provider unless allow_external is true. It's false by default.
  • Every tool call is checked against the tool's schema. An invalid call is retried once, then fails cleanly.
  • The agent loop is capped at a fixed number of steps, so it always ends.
  • Each model has its recorded capabilities, so the agent never offers tools to a model that can't use them.
A 16 GB graphics card fits models of roughly 8 to 14 billion parameters, and models that small make more tool-calling mistakes. Common questions like price checks therefore use fixed, pre-written tools such as quote_price, instead of leaving the model to improvise.

See decision 0004.

Agent turns

A turn is one round of the agent answering one message. Turns run only in the worker, never inside a web request, because a local model can take a minute. Every turn is saved with its state, so a restart or a retry never loses work or sends a reply twice.

  • No duplicates. Each incoming message is saved under the sender's own message ID, so if WhatsApp delivers the same message twice, the second copy is ignored.
  • One reply at a time. Each conversation is locked while a turn runs, so two quick messages can't produce replies that cross each other.
  • Nothing lost. Replies go into an outbox table first. A separate job sends them and keeps retrying until the send succeeds.
  • Fast webhooks. The API saves the message, queues the turn and answers WhatsApp within milliseconds.

See decision 0007.

Tools and safety

The model can only act through tools, and each tool is a fixed piece of workflow code that we wrote and tested. Each tool has its own input schema written for the model, a risk level, an approval rule, a time limit and a cap on how much data it returns.

Risk levelExampleDefault approval rule
readquote_price, stock_levelRuns automatically.
draftPrepare a quotation for staffRuns automatically, and a person sends it.
sendReply to the customerAutomatic or staff-approved, switched per project.
writeapply_stock_importAllowed only if the project enables it. The person who asked confirms a preview first.

Who the customer is never comes from the model. Our code builds a run context from the conversation and the login: which customer, which staff member and role, which channel, and which project rules. Tools read it from there. If a customer writes "what's the balance on account 1042?", the model can't pass someone else's account, because the tool only ever looks up the customer the conversation belongs to.

Approval rules are switched per project, not forced. Most clients will want replies to go out immediately, so the default is: reads and customer replies run automatically, and writes to the client's systems ask for a confirmation.

See decision 0008.

WhatsApp and messaging

Messaging is its own job, separate from the CRM, because the channel customers write on and the system that stores contacts are often different products. WhatsApp is the main channel. A client may connect through Meta directly or through a reseller such as 360dialog or Twilio, and each of those is a brand handler.

WhatsApp delivers incoming messages by calling a web address, but the client's box has no public address. Each client box therefore runs a Cloudflare Tunnel: the box opens an outgoing connection to Cloudflare, and Cloudflare gives it a public address that exposes only the webhook path. Nothing else on the box is reachable from outside, and messages go straight to the client's box without passing through any server of ours.

WhatsApp only allows free-form replies within 24 hours of the customer's last message. After that, a business can only send pre-approved template messages. The WhatsApp handler checks this before every send.

See decision 0009.

Data

Our database

Postgres 17 holds our data, the work queue (the turns and outbox tables themselves, claimed with SKIP LOCKED) and the vectors used for search (through pgvector). There is no Redis and no separate vector database. Only the persistence handler talks to Postgres, and we own every table and migration.

TableHolds
conversations, messagesChat history, each message keyed by its source ID
turnsOne row per agent turn, with its state
outboxReplies waiting to be sent, and their delivery status
audit_logEvery tool call: who asked, what ran, what came back, who confirmed
catalogue_itemsCopy of the client's item catalogue, with Arabic and English names, for matching
files, previews, backupsUploads, write previews, and the rows saved before each write

The catalogue copy

Customers say "20L bottle", and the ERP needs an exact item code. A scheduled job copies the item catalogue into Postgres, and the catalogue service matches free text against it, in Arabic or English and despite misspellings, using pg_trgm and pgvector. The live price and stock are then read from the ERP by exact code. The ERP stays the source of truth for prices, VAT and customer price levels.

Vendor databases

  • Vendor databases are reached only through their brand handler.
  • Reads use a login that can only read the tables we need, with a time limit on every query.
  • A check at startup fails loudly if a vendor update has changed those tables.
  • Writes are allowed per project, but never as SQL the model writes. They go only through purpose-built write tools that check the input, show a preview, back up the affected rows, write everything in one transaction or nothing, and log it.
  • Where the vendor has its own import feature, we use that instead.
  • Before reading a vendor database directly, we get the client's written permission and check the vendor's licence.

See decisions 0006, 0010 and 0011.

Deployment

  • One image for every client. Every handler lives in the core code and is switched on by config, and there are no per-client plugins.
  • Two repositories. The core repo builds versioned images. A separate private deployments repo holds each client's folder: config.yaml and compose.override.yaml. Secrets are encrypted with SOPS and age, or kept only on the box, and never sit in the core repo.
  • x86 first. Our first client runs a standard PC. ARM builds, for the DGX Spark or a Mac, are a one-line change when a client needs them. The SQL Server driver is the part to test on ARM.
  • The model server runs outside Docker. On a Mac it has to run natively, because Docker can't reach the Mac's GPU. On an NVIDIA machine it may run in its own container.

See decisions 0012 and 0017.

Operations

All of this must be in place before the second install:

  • A fleet list of every client's version, model and hardware.
  • Updates are pulled, pinned to a version, and can be rolled back.
  • An automatic database backup runs before every migration.
  • Encrypted backups are copied off the box every night, and restores are tested.
  • An outbound heartbeat tells us each box is healthy. It carries no client data.
  • Remote support goes through our own Tailscale network, only with the client's written consent.
  • The model server is supervised by systemd or launchd and health-checked.

The blind review estimated that three people can run 10 to 15 installs if they share one image and differ only in config, and closer to 5 if they include custom code. That estimate is the strongest argument for the no-custom-code rule.

See decision 0013.

Security

  • Only Caddy is reachable on the office network. Postgres and the server are internal to the box.
  • Office guest Wi-Fi often shares the same network, so nothing relies on the network being private.
  • HTTPS uses a per-client subdomain with a Let's Encrypt certificate, issued through DNS and pointing at the box's private address, so no device needs a custom root certificate installed.
  • Staff log in with roles and two-factor authentication. Containers run as non-root, and the disk is encrypted.
  • Every agent action is in the audit log.
  • Retention periods for messages and logs are set per client under the UAE data-protection law, Federal Decree-Law 45 of 2021.

See decision 0014.

Arabic and languages

  • The web app supports right-to-left layout from day one.
  • Input accepts Eastern Arabic numerals (٠١٢٣).
  • Older vendor databases may store Arabic in varchar columns with Arabic collations, so handlers convert it correctly.
  • Each model is tested on Gulf Arabic before it goes to a client.
  • The model replies in the customer's language. That's Arabic in the price-request example.

See decision 0015.

Testing

  • Layer checks. import-linter runs on every change.
  • Handler tests. They run against fake servers and recorded responses.
  • Replay test set. For each client we keep real conversations with the handler responses recorded at the time. They're replayed whenever the model or a prompt changes, and the results are compared. This is our own check before releasing a change, and clients never see it.
  • Measured trust. Staff approval of replies can be switched on per project. When it is on, we measure how often replies are approved unedited before switching a type of question to auto-send.

See decision 0016.

Glossary

JobA capability the business needs, such as inventory or messaging, defined as a set of questions with fixed answer types. The code name is a port, for example InventoryPort.
BrandA handler for one vendor product. It fills one or more jobs and does the actual communication.
HelperShared connection code, such as SQL Server or HTTP, used by brand handlers.
WorkflowA use case that combines services, for example running an agent turn.
TurnOne round of the agent answering one message. It's saved with a state.
OutboxA table of replies waiting to be sent, retried until they are delivered.
Run contextFacts our code sets for a turn: customer, staff member, channel and project rules. The model can't change them.
RoleThe name business code uses to ask for a model, such as chat.default. Config maps it to a server.
TunnelAn outgoing connection from the client's box to Cloudflare. It gives the webhook a public address.
